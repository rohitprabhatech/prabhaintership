# Manual Testing Guide

**Application:** Prabha Technology Pvt. Ltd. Internship Management System  
**Repository-verified stack:** React 19 + Vite, Python 3.11+ + FastAPI, SQLAlchemy 2.x, MySQL/PyMySQL, Alembic, Pydantic, Argon2 via `pwdlib`.  
**Status:** Prepared from source inspection. Manual cases have not been executed; see [09-manual-test-cases.md](./09-manual-test-cases.md).

## 1. Safety First

1. Use only a development or isolated QA environment that the database owner has approved for adding synthetic records. The configured local schema is `internship_management`; prior QA activity wrote test-generated rows there. Do not treat it as a clean production-like dataset.
2. Do not run test setup, migrations, SQL writes, deletes, truncates, or resets against production. Do not use real financial transactions, payment credentials, student contact data, or passwords in screenshots.
3. The SQL in this guide is read-only. It intentionally does not select `admins.password_hash` or any other secret.
4. Create sample records through the UI only. Do not insert test rows with SQL. Keep the `MANUAL-2026` marker in test identifiers to distinguish your records. Do not remove test records unless the owner separately approves a documented cleanup.
5. Use a dedicated QA Admin where possible. Avoid repeatedly testing invalid credentials on the sole working Admin; the existing login limiter can temporarily block a client address.
6. Never share entered passwords, access tokens, complete `.env` files, or screenshots containing credentials.

## 2. What Is Implemented

The application uses a single Admin role. The actual login screen is `http://localhost:5173/login`; the API is rooted at `/api/v1`. The dashboard navigation includes Overview, Students, Programs, Batches, Enrollments, Finance, Projects, Certificates, Reports, and Change password.

| Area | Implemented workflow and important boundaries |
| --- | --- |
| Admin authentication | Username/password login, bearer JWT, protected APIs, client-side sign out, login rate limiting, and token invalidation using `auth_version`. No server logout endpoint or student login exists. |
| Change password | Authenticated Admin enters current password, new password, and confirmation. Password must be 12–1024 characters and differ from the current password. On success, old JWTs are invalidated and the UI requires login again. |
| Programs | Create with a required positive duration, search, filter by status, paginate, edit name/duration/description/status, deactivate/reactivate, and preview linked records before deletion. Program code is generated by the backend. |
| Batches | Create under an active program, filter by program/status, paginate with live total-enrollment, active-enrollment, and distinct-active-student counts, open a searchable/paginated roster with fee summaries, edit name/dates/capacity/status, cancel, and preview linked records before deletion. Batch code is generated and unique across programs. |
| Students | Create a profile alone or select an active program and eligible batch to create the student, enrollment, and initial fee term in one transaction; search/filter/paginate, view the profile and enrollment history, archive/reactivate, and preview enrollment links before deletion. Student number is generated; profile fields include full name, optional email/phone/address/city/state/postal code/institution/course/internship domain. |
| Enrollments | Create for an active student and required eligible batch; the program is derived from that batch. The backend generates the enrollment number and records the initial fee term in the same transaction. Status changes are terminal (completed, withdrawn, or cancelled); linked history blocks deletion. |
| Finance | View authoritative enrollment balances, fee terms, adjustments, payment history; revise terms, adjust fees, record installments, refund or reverse receipts. Amounts use INR decimal precision. |
| Projects | Create/archive/reactivate project definitions; assign to enrollment; move assignments through supported progress states. Linked assignments block project deletion. |
| Certificates | Issue certificate with a type; the backend generates the certificate number. View/report/search; record replacement, revocation, correction, and event history. The backend currently checks that the enrollment exists, not project completion or fee clearance. |
| Overview | KPIs are assembled from existing student/program/batch/enrollment/certificate/fee APIs. Recent enrollments are shown. The “Recent payments” panel intentionally explains there is no global recent-payment endpoint. |
| Reports / exports | A Reports page exists, but the API contract does not implement general reports or CSV export. Treat export testing as blocked, not as a failed supported workflow. |
| Fee structures | A `fee_structures` database table exists, but no fee-structure management API or UI was found. The manual enrollment flow sets the initial agreed fee directly; do not attempt to create/select a fee structure in the UI. |

## 3. Start the Application

Run each command in its own PowerShell terminal. The backend reads the local `backend/.env` by repository path.

Backend (from repository root):

```powershell
.\backend\.venv\Scripts\Activate.ps1
Set-Location backend
python -m app.cli verify-db
python -m alembic current
uvicorn app.main:app --reload --host 127.0.0.1 --port 8000
```

Frontend (from another terminal at repository root):

```powershell
Set-Location frontend
npm run dev -- --host 127.0.0.1
```

Open `http://localhost:5173/login`. If a port is already occupied, choose a free port and update the frontend API base / backend CORS configuration as described in [07-local-setup-and-run.md](./07-local-setup-and-run.md). Do not terminate an unknown listener.

To stop processes you started, use their terminal `Ctrl+C`; do not terminate unrelated processes by name.

## 5. Beginner End-to-End Test Order

Follow [09-manual-test-cases.md](./09-manual-test-cases.md) and record results before proceeding.

1. **Sign in:** Open the login URL. Enter the provisioned Admin username and password. Confirm the Overview page appears. Test invalid credentials only in a safe environment and stop when the rate limiter blocks further attempts.
2. **Change password:** Use the Change password sidebar item. For manual testing, only use an Admin account you are authorized to change. Verify wrong current password, mismatched confirmation, too-short password, and reusing the old password are rejected. Complete a successful change only when you intend to replace that QA Admin credential; the feature invalidates the current token and signs you out.
3. **Create the program:** Open Programs → Add program, enter the sample name, duration, description, and status, then save. Verify the generated code; test status filtering and edit duration/description/status.
4. **Create the batch:** Open Batches → Add batch, select the active sample program, enter the name/dates/capacity, save, and verify its generated code and roster. Invalid dates or a non-active program must not create a batch.
5. **Create the student:** Open Students → Add student. Enter the sample name and optional profile/contact fields. Verify the generated student number. Open the profile, edit a harmless synthetic value, refresh, and confirm persistence. Do not put a real person's details in the QA schema.
6. **Create the enrollment:** Open Enrollments → New enrollment. Select the sample student and required batch, enter dates, fee, and reason. The program should be derived from the selected batch. Review and confirm; verify the generated enrollment number. An active duplicate tuple (student/program/batch) should be rejected.
7. **Check fees/payments:** Open Finance, locate the sample enrollment, and check the initial balance. Add each of the three synthetic installments separately; compare the displayed pending balance to the table above. The Finance UI requires review/confirmation before committing writes.
8. **Test adjustments only if needed:** In the enrollment finance detail, use a synthetic reason. Fee adjustments are discounts or increases; payment adjustments are refunds or reversals. These append-only ledger actions change balance and are not a substitute for cash movements.
9. **Create and assign project:** Open Projects, create the project, assign it to the sample enrollment, then transition it from assigned to in progress to completed. Confirm completion is timestamped. Do not expect arbitrary state transitions to be accepted.
10. **Issue certificate:** Open Certificates → Issue certificate. Select an enrollment, enter the type, and confirm. Verify the generated number in its report/detail and event history. Source inspection found no completion/fee-clearance eligibility rule beyond requiring an existing enrollment; record this as a business-rule gap rather than assuming eligibility is enforced.
11. **Cross-check Overview:** Refresh Overview and compare counts/balances to UI pages and the read-only SQL in Section 7. The dashboard fee totals are calculated from API fee summaries; the browser does not invent balances.
12. **Regression/security/UI:** Check navigation, sign out, protected routes, keyboard operation, viewport sizes, loading/errors, and safe response/log behavior. Reports/export is documented as unavailable, not a supported pass case.

## 6. Implemented Constraints to Test

- Password: 12–1024 characters for new/change/reset flows; new password cannot equal current password.
- Program: nonblank name, positive duration in months, generated unique code; create status is Draft or Active; update status is Draft, Active, or Inactive. Existing duration values may remain null until edited.
- Batch: requires an active program; end date cannot precede start date; capacity must be positive or blank/unlimited; generated code is globally unique. Capacity cannot drop below active enrollments; edited dates cannot exclude existing enrollment dates.
- Student: full name is required; student number is generated; email must be valid and unique case-insensitively when supplied; added profile fields are optional.
- Lifecycle safety: archive/deactivate/cancel and permanent-delete requests require a 1–500 character reason where applicable. Each list exposes a dependency preview for permanent deletion. Deletion is blocked with a conflict when linked history exists; database foreign keys protect against concurrent references. Audit history is retained. Prefer archive/deactivation/cancellation when a record has history.
- Enrollment: requires an active student and a batch belonging to an active program; program is derived from the batch. The batch must accept enrollment, fit dates, and have capacity; duplicate active student/program/batch tuple is rejected. Dates must be valid and end cannot precede start.
- Enrollment lifecycle: active → completed, withdrawn, or cancelled; terminal states cannot be reactivated.
- Sensitive status changes (student archive, program deactivation, batch cancellation, enrollment withdrawal/cancellation, project archive, and project-assignment cancellation) require a reason and create an Admin audit event. Cancellations never automatically refund payments or change fees.
- Money: positive amounts with at most two decimal places; currency is INR; send exact decimal strings. Overpayment is rejected. Payment/adjustment writes require idempotency keys; financial data is not sent to a real payment processor.
- Project assignment: unique project/enrollment pair. Supported transitions are assigned → in progress/cancelled and in progress → completed/cancelled.
- Project/certificate: project codes and certificate numbers are generated. Issued certificates are not edited/deleted; replacement/revocation/correction are recorded as history events. Finance records are not deleted; refunds/reversals are append-only, and certificate revocation/replacement preserves issuance history.
- API authentication: all operational APIs require a bearer token except health and login. JWT invalidation checks the Admin row's `is_active` and `auth_version`.

## 7. Read-Only MySQL Verification

Use only an authorized MySQL client connected to the correct schema. The following SELECTs contain discovered table/view and column names. They do not retrieve Admin password hashes and do not modify rows. Add a time/filter predicate for large production datasets; these examples are for the small, approved QA dataset.

```sql
SELECT admin_id, username, email, is_active, auth_version, created_at, last_login_at
FROM `internship_management`.`admins`
ORDER BY admin_id;

SELECT student_id, student_number, full_name, email, phone, status, created_at, archived_at
FROM `internship_management`.`students`
ORDER BY student_id;

SELECT program_id, program_code, name, status, created_at
FROM `internship_management`.`internship_programs`
ORDER BY program_id;

SELECT batch_id, program_id, batch_code, name, starts_on, ends_on, capacity, status
FROM `internship_management`.`batches`
ORDER BY batch_id;

SELECT enrollment_id, enrollment_number, student_id, program_id, batch_id, status,
       starts_on, ends_on, created_at
FROM `internship_management`.`enrollments`
ORDER BY enrollment_id;

SELECT fee_structure_id, program_id, name, standard_amount, currency, is_active, created_at
FROM `internship_management`.`fee_structures`
ORDER BY fee_structure_id;

SELECT fee_term_id, enrollment_id, fee_structure_id, agreed_amount, currency,
       effective_from, effective_to, reason, created_by
FROM `internship_management`.`enrollment_fee_terms`
ORDER BY enrollment_id, effective_from;

SELECT fee_adjustment_id, enrollment_id, adjustment_type, amount, reason, approved_by, approved_at
FROM `internship_management`.`fee_adjustments`
ORDER BY fee_adjustment_id;

SELECT payment_id, enrollment_id, amount, currency, paid_at, payment_method,
       payment_reference, recorded_by
FROM `internship_management`.`payments`
ORDER BY enrollment_id, paid_at, payment_id;

SELECT payment_id, enrollment_id, amount, adjusted_amount, net_amount, derived_status
FROM `internship_management`.`v_payment_status`
ORDER BY enrollment_id, payment_id;

SELECT enrollment_id, enrollment_number, student_id, program_id, batch_id,
       enrollment_status, fee_term_id, fee_amount, currency, adjustments_total,
       effective_fee, net_paid, pending_balance
FROM `internship_management`.`v_enrollment_balances`
ORDER BY enrollment_id;

SELECT project_id, project_code, name, status, created_at
FROM `internship_management`.`projects`
ORDER BY project_id;

SELECT project_assignment_id, project_id, enrollment_id, status, assigned_at,
       completed_at, assigned_by
FROM `internship_management`.`project_assignments`
ORDER BY project_assignment_id;

SELECT certificate_id, enrollment_id, certificate_number, certificate_type,
       issued_at, created_at, replaces_certificate_id, issued_by, derived_status,
       terminal_event_at
FROM `internship_management`.`v_certificate_status`
ORDER BY certificate_id;

SELECT certificate_event_id, certificate_id, event_type, related_certificate_id,
       occurred_at, reason, recorded_by
FROM `internship_management`.`certificate_events`
ORDER BY certificate_id, occurred_at, certificate_event_id;
```

If a certificate view query reports an unknown `created_at` column, check the Alembic revision; migration `0008` adds that column to `v_certificate_status`. Do not apply migrations to production as a test step.

## 8. Test Commands and Recordkeeping

Automated backend unit tests:

```powershell
Set-Location backend
.\.venv\Scripts\Activate.ps1
python -m pytest -q -m "not integration"
```

Backend MySQL integration tests require `APP_ENV=test`, a dedicated, disposable `*_test` schema, and matching `TEST_DATABASE_URL` and `DB_NAME` set before Python imports application modules. Never point test settings at `internship_management` or production. Follow `backend/tests/conftest.py`; it checks the configured DB name and refuses the application schema. The full test command skips database-backed tests when no isolated test URL is configured.

Frontend tests and production build:

```powershell
Set-Location frontend
npm test -- --run
npm run build
```

For each manual case in [09-manual-test-cases.md](./09-manual-test-cases.md), record the date, tester, environment/schema name (no credentials), actual result, status, and evidence file path. Leave it **Not Run** until the steps have actually been performed. Capture only synthetic data and redact tokens/contact data before saving evidence.
